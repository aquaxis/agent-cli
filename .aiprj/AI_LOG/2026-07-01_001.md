## read→LLM report (FR-12)

**Status: implemented.** The "read a file then send its content to the LLM"
feature is already implemented and requires no new mechanism.

Mechanism — `src/agent.rs` `process_turn()`:

```rust
for _ in 0..max_iterations {
    let specs = self.tools.specs();
    let mut stream = self.provider.complete_stream(&self.history, &specs).await?;
    // collect ProviderEvent::ToolUse { id, name, args } ...
    let result = self.tools.get(&name).unwrap().invoke(args, &ctx).await?;
    self.history.push(Message::ToolResult {
        tool_use_id: id,
        content: result.content,   // <- the read file content lands here
        is_error: !result.ok,
    });
    // loop: the next complete_stream(&self.history, ..) re-sends the full
    // history (now including the ToolResult) to the provider.
}
```

`read` (like the former `fs_read`) returns `ToolOutput::ok(content)` where
`content` is the file text. `process_turn()` wraps that in a
`Message::ToolResult` pushed onto `self.history`, and the next loop iteration
calls `self.provider.complete_stream(&self.history, &specs)`, so the read
content is sent to the LLM on the next provider call.

Verification: the new agent test `read_tool_result_carries_file_content` issues
a `read` tool call for a temp file containing `READABLE_MARKER_42` and asserts
the `AgentEvent::ToolResult { name: "read" }` output contains that marker.
Combined with the existing `agent_completes_tool_use_cycle_with_bash` test
(which proves `process_turn()` pushes `ToolResult` into history and re-calls
the provider for the next turn), this confirms the read file content reaches
the LLM.
