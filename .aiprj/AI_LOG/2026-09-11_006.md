## 3. Findings that shaped the specification

- **The observed run is the requirement.** Asked in Japanese for a multi-agent
  investigation, the model spawned four children with per-topic prompts (a fifth
  refused by `[spawn] max_children`, the limit added in the previous cycle doing
  its job in a real scenario), collected three with `wait_reply` — one hit the
  120 s timeout because that child was still busy with its first task, since an
  agent takes one input at a time — and combined them. Then the slow child
  reported back on its own, which arrived as a **peer prompt** and started
  another turn in the parent: a provider call whose answer had no recipient.
  That is the "返す相手のいない応答" the instruction names.
- **Half of it already exists.** `AgentInput::Context` — append one message, no
  turn, no event, no provider call — was built in v0.15.0 for `!` shell output.
  It has no way in from IPC, which is the whole gap.
- **A new IPC variant is safe.** An unparsable line, including an unknown
  `kind`, is answered with `Error { message: "parse error: …" }` and the
  connection stays up. A new message sent to an older agent is therefore a
  readable signal, which is what makes a fallback possible rather than a
  version negotiation.

## 4. Key decisions

| Decision | Reason |
|---|---|
| A new `IpcMessage::Context { from, from_name, text }`; the seven existing variants untouched | Adding a variant to a tagged enum leaves the others' encoding alone, so a mixed-version registry keeps working (FR-01, P-3). |
| The sender chooses: `delivery: "prompt" \| "report" \| "ask"` | Only the sender knows whether it is answering or asking. `wait_reply: true` stays as an alias so existing calls keep working (FR-05, FR-06). |
| The receiver reuses `AgentInput::Context` | The no-turn append is already built and tested; this cycle gives it a second source, not a second mechanism (P-2). |
| One `Info` line on arrival, not the text | Several thousand-character reports would bury the session; the text belongs in the conversation, and the log keeps it in full (FR-04, AS-06). |
| An older peer's `Error` triggers a fallback to a prompt, reported to the model | Degrade, do not fail: the text still arrives, and the model is told the peer will answer instead — the two things that change what it does next (FR-08, P-4). |
| The arrival is attributed with the same header shape a peer prompt uses | Several children report in; the model has to tell which is which, and one header shape is easier to read than two (FR-03, P-6). |
