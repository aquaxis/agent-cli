## Specification session

Baseline BL-01 – BL-18 established against the clean v0.19.0 tree.

**The finding that opened the cycle**: `.agent-cli/settings.json` was committed,
tracked, and **read by no line of code** — a copy of `.claude/settings.json`
with ten deny rules and twenty-three allow rules, added in commit `a2bbcd7`. A
grep for `settings.json` across every source and document outside `target/`
returned nothing. The repository shipped a file saying `Bash(rm -rf ~/**)` was
denied while agent-cli would run it without a murmur. Not a missing feature — a
false promise, and the reason "silence is never the answer" became the cycle's
second principle.

Two more: gating was **whole-tool or nothing** (`[tools] enabled` ∩ persona
lists, decided once at startup — no rule could mention an argument), and
approval was **all-or-nothing** (one `AtomicBool` that `/auto on` flips for
everything).

Three shapes were weighed: **A** a separate `.agent-cli/settings.json`, **B**
`[permissions]` in `config.toml`, **C** both. C was rejected outright — two
sources for one truth is a precedence question with no defensible answer.

A was recommended first. The recommendation was **changed to B** when the cost
of carrying two formats was put to it. Two arguments decided it: a permissions
file needs **comments beside each rule** — a deny rule's *why* matters as much
as the rule — and JSON has none; and A's headline benefit, "paste your Claude
Code file", does not survive the finding that such a file is **partly inert here
anyway** (`MultiEdit` has no agent-cli equivalent, `acceptEdits` has no meaning,
`statusLine` / `env` are ignored), so it must be reviewed line by line
regardless, which costs more than retyping.

**Decisions**: D-1 `[permissions]` in `config.toml`, TOML only. D-2
`.agent-cli/settings.json` deleted. D-3 both `config.toml` files effective and
merged, project-local winning.

D-3 was raised during the session and turned out to be a track of its own:

- **BL-09** — resolution **selected one file and did not merge**. A project
  `config.toml` made the user-level file invisible *in its entirety*, not just
  where it overrode. Fixing that also touched `ConfigSource` (~15 call sites)
  and the auto-generation rule.
- **BL-12** — a detached child was launched with `--config <one path>`, so under
  a chain it would silently drop the base layer, and with it any machine-wide
  `[permissions] deny`. **A detached agent running under weaker rules than the
  agent that spawned it** was the quietest failure in the cycle, and FR-05 exists
  to prevent it.

The priority direction of the merge was ambiguous in the instruction as given
and was confirmed with the user: **project-local wins**.

Also recorded: **BL-18**, a pre-existing failure. `cargo test -- --test-threads=1`
gave 520 + 4, 0 failed, while a plain `cargo test` reproducibly failed
`a_selection_copies_the_line_the_terminal_wrapped_as_one_line`. Not this cycle's
fault — it came in with v0.19.0 — but it blocked the cycle's acceptance, so it
was given its own task rather than being folded into a feature commit or
redefined away as "green under `-j1`".

## Execution session

### T-02 / T-03 — the configuration track, first

Verified before the permissions work, because the rules are carried by the thing
it changes. `ConfigSource` gained an ordered `layers` chain with `path()` over
the top one — which kept the ~15 call sites to a one-character change — and
`config::merge` combines layers as `toml::Value` *before* `Config` is
deserialized, so every section is layered without its own merge code.

Tables merge recursively; scalars and arrays are replaced; `permissions.deny`
and `permissions.allow` **union**. That one exception is P-1 expressed in the
merge: under replacement a project file could delete a machine-wide deny rule by
redefining the list, and a project directory is exactly the thing a user may not
have written.

`--config` became repeatable (`Vec<PathBuf>`, `num_args = 1`), and
`spawn_detached` now emits one per layer. The two selftest children were
deliberately **left** on a single `--config`: they generate a throwaway config
and isolation is the point there.

### T-04 / T-05 — the permissions track

`src/permissions.rs`, pure throughout: `Rule`, `Pattern::{Any, Prefix, Domain,
Glob}`, `canonical_tool` folding case and `_`, `subject_of` fixing one gated
argument per tool, and `Ruleset::decide` scanning deny in full, then allow, then
`default_mode`.

Three decisions worth recording. `bash()` is **rejected** rather than read as
"every bash call" — an empty pattern silently widening to the bare-tool form
would be a booby trap in a deny list. An unknown tool name **keeps** its rule so
`/permissions` still shows what the user wrote; it simply never matches, and
says so. And `host_of` falls back to the whole string when a URL does not parse,
so a malformed URL is still matchable rather than silently escaping every domain
rule.

The decision block sits in `agent.rs` immediately before the `auto_approve`
check. A `Deny` never consults `auto_approve` — which is what makes the rules
usable for `run_headless`, whose agent auto-approves unconditionally because it
has no console to ask at. That is the concrete reason the behaviour change is
worth making.

### T-09 — the flaky test

The design guessed the racers were tests touching the global transcript without
`scroll::test_lock()`. **They were not**: every test that installs a transcript
already took it. The real writers are indirect — the four `raw_*` REPL writers
tee into the transcript, so any test exercising a printing path appends to
whatever transcript another test happens to have installed, with no idea it is
writing at all.

Fixed at the source instead: under `cfg(test)`, recording is gated on the thread
that installed the transcript. Production is untouched.

### T-10 — verification

`cargo build` clean; `clippy --all-targets` at **8 warnings, the same 8 as the
baseline**, confirmed by stashing the work and re-running; `cargo test` green at
**562 unit + 6 integration, 0 failed in a default parallel run**, run five times

The live run was driven by a 25-line mock `/api/chat` provider so a real
`agent-cli run` process would issue a real tool call, with `auto_approve_tools =
true` in the config **and** `/auto on` typed at the prompt:

```
> [tool-call] bash {"command":"rm -rf /tmp/permcheck/victim"}
[tool-result ERR] bash: denied by permission rule: bash(rm:*)
```

`PROOF.txt` inside that directory still exists afterwards. That is the evidence
C-06 asked for: the refusal was observed, and the destructive command was never
let through. The following allowed call (`git status --short`) ran with no
prompt, `/permissions` showed both layers with `deny (3)` — the user's two
unioned with the project's one — and `!rm --version` ran unaffected, since `!`
is the user's own typing and is never gated.

## Deviations from the design

Four, all recorded in `AI_PRJ_DESIGN.md` §13.2: the layer union de-duplicates;
`ConfigSource::path()` returns an owned `PathBuf` for the benefit of a
default-constructed source; **no `settings.rs` module was needed** once option B
removed the second file; and the live verification was driven by a mock provider
rather than by hand.

## Notes for whoever picks this up next

- The `[permissions]` rules are a **guardrail against mistakes, not a sandbox**,
  and `doc/config.md` §12.6 says so with the four commands that get around
  `bash(rm:*)` spelled out. That honesty is load-bearing: a reader who believes
  otherwise is worse off than one with no rules at all.
- Two user-visible behaviour changes are in `CHANGELOG.md` under `Changed`, not
  buried in `Added`: the config merge (anyone with both files will start seeing
  user-level keys that the project file does not override) and `deny` outranking
  auto-approval.
- A new tool needs an entry in `permissions::subject_of`, or an explicit record
  that it has none. `CONTRIBUTING.md`'s checklist now says so.
