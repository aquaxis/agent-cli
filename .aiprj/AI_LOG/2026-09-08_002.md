## 2. What was built

While the progress indicator is drawing, a tool result is wrapped to the
terminal width and shown as at most five rows:

```text
[tool-call] bash {"command":"seq 1 300"}
[tool-result ok] bash: {"exit_code":0,"stderr":"","stdout":"1\n2\n3\n4\n5\n6\n7\
… +14 more lines
⠸ 0.4s
```

- `compact_tool_result(mark, name, output, cols, max_rows)` is a pure function:
  it wraps the whole `[tool-result …]` line with `editor::wrap_display`, keeps
  the first `TOOL_RESULT_ROWS` (5) rows and appends `… +N more lines`. A result
  that already fits is returned verbatim.
- It is driven by the same flag that shortens the tool call, renamed
  `DisplayState::compact_output` now that it governs both neighbours of the
  indicator. With `[ui] show_progress = false`, on a non-TTY and in `serve`
  mode, the historical full output is unchanged.
- Display only: the model receives the complete tool result and the conversation
  log keeps it.

## 3. Decisions worth recording

| # | Decision | Reason |
|---|---|---|
| 1 | The **head** of the result is kept (the `thinking` view keeps its tail). | A result is read from the top, and the original instruction asks to show up to a point and elide the rest; a live progress view instead wants its newest rows. |
| 2 | No click toggle for tool results (AS-11). | Unlike the `thinking` block, a printed result is permanent scrollback: once later output exists it cannot be re-rendered in place. The full text is in the conversation log, and `show_progress = false` prints it verbatim. |
| 3 | The five rows are counted **after wrapping**, so one very long line also counts as several rows. | The point of the limit is how much screen the result takes, not how many `\n` it contains — a `bash` result is JSON with escaped newlines, so a line count alone would not bound it. |
