## 3. What was found

`instructions.md` had been **replaced**. The previous cycle (peer results as

### The cause

| Step | Result |
|---|---|
| `GET https://opencode.ai/zen/go/v1/models` | `HTTP 200`, 37 model ids — the endpoint is up and the subscription is live |
| `POST .../zen/go/v1/chat/completions` with exactly the headers agent-cli sends | **`HTTP 400`** `{"type":"error","error":{"type":"MissingSessionID","message":"Error from provider (Console Go): Request is missing x-opencode-session and cannot be routed efficiently. Please see https://opencode.ai/docs/go/#where-can-i-use-it"}}` |
| The same request plus `x-opencode-session: ses_test_agentcli_0001` | **`HTTP 200`**, a normal completion |
| The Anthropic surface `.../zen/go/v1/messages`, both ways | Identical: fails without, succeeds with |
| `https://opencode.ai/docs/go/` | Requires a client to "Send a stable session ID in `x-opencode-session` for each conversation" and to identify itself with its own user agent rather than a generic HTTP-library name; lists other CLIs broken by the same change |

Nothing in `agent-cli` broke and no key expired. OpenCode Go added a routing
requirement after v0.17.0 shipped. `src/ai/opencode.rs` sends `content-type`,
`Authorization: Bearer` (and `x-api-key` + `anthropic-version` on the Anthropic
surface) and nothing else, and its `reqwest` client sets no user agent — so
every Go request is rejected before a model is reached, on both wire formats,
for every model, for any config whose `base_url` is a Go endpoint. That includes
the installed `~/.config/agent-cli/config.toml`, which uses `kind = "opencode"`
rather than the `opencode-go` shortcut.

### Two defects found beside it

- The `opencode-go` shortcut fills `model = "claude-sonnet-4-5"` and
  `api = "anthropic"`, but the Go endpoint serves **open-weight models only** —
  no `claude-*` id at all (those are on `.../zen/v1`). It answers `Model
  claude-sonnet-4-5 is not supported`, so a fresh shortcut config cannot work
  even once the header is sent.
- That error arrives with `HTTP 401`, and `derive_hint`'s `401` rule then tells
  the user the API key "is invalid or has been revoked" — pointing at a key that
  is fine. The real `400 MissingSessionID` gets no hint at all.

## 4. Decisions taken into the specification

- The header goes on **every** cloud request, not only on a URL containing
  `/zen/go/` — a Go host behind a proxy would defeat sniffing, and a stable id
  is what the rest of Zen wants too.
- The id is a `ses_<ulid>` minted at provider construction: stable for an
  agent's conversation, distinct between agents, no new plumbing, and not reset
  by `/clear` (it is a routing and prompt-cache key, not conversation state).
- Recovery must need **no configuration change** — upgrading is enough. The new
  `session_id` key is an override, never a prerequisite.
- Request construction is extracted into a pure `CloudRequest` so the header is
  proved by a test rather than by reading the code.
- The two defects above are fixed in the same cycle: the header alone would
  leave a fresh `opencode-go` config failing with "your key was revoked".

One assumption was flagged explicitly for the user (AS-01): the instruction asks
for the **cause**, and the cycle also fixes it. T-02 stands alone as the
investigation if only that was wanted.
