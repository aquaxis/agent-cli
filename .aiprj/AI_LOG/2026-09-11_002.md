## 3. Findings that shaped the specification

- **The safety property is structural.** A submitted line is classified only
  inside the two input loops, and a peer's prompt bypasses that entirely,
  arriving as `AgentInput::PeerPrompt` (BL-01, BL-02). Putting the `!` branch
  next to the `/` branch therefore means no peer, and nothing the model
  produces, can reach command execution — it is not a check that could be
  forgotten. An explicit test is specified for it anyway (AC-07, V-6).
- **The missing plumbing is "add context without a turn".** `AgentInput` has no
  variant that appends to the conversation without starting one (BL-05), and
  Claude Code's bash mode is defined by the output becoming context. One new
  variant plus a four-line handler covers it (design §6).
- **Handing the terminal over is the expensive option.** In raw mode `Ctrl-C` is
  a key; if raw mode were suspended to give a child the terminal, `Ctrl-C` would
  reach agent-cli's own SIGINT handler and shut the REPL down (BL-09). Proper
  job control (process group + `tcsetpgrp`) would be needed. Piped execution
  also keeps the output inside the writers, where the v0.14.0 scrollback can see
  it (BL-08) — output written straight to the terminal would be invisible to the
  wheel.

## 4. Key decisions

| Decision | Reason |
|---|---|
| `!<command>`, classified where `/` is (FR-01) | Structural safety (BL-02), and no collision with the command table or custom-command prefix matching. |
| Piped stdio, no pty, no terminal handover (AS-01) | Keeps raw mode, `Ctrl-C` and the scrollback intact (BL-08, BL-09). Interactive and full-screen programs are explicitly out of scope, as they are in Claude Code's bash mode. |
| Output **streamed** line by line, not captured whole (FR-06) | A long `!cargo build` shows progress, and each line lands in the transcript as it arrives — unlike the `bash` tool, which returns everything at the end (BL-03). |
| Output appended as a **`Message::User`** (AS-06) | A fabricated `ToolResult` would need a `tool_use_id` and could unbalance an assistant message's `tool_calls` (BL-06). |
| No approval gate (FR-03, AS-02) | The gate exists because a tool call is the *model's* decision; a typed `!` is the user's. `[shell] enabled = false` is the off switch. |
| Screen complete, context capped (FR-09) | `!cat big.log` must not silently consume the context window, but the reader should still see everything. |
| A fourth prompt state with its own `select!` arm (FR-07) | The loop stays responsive, so `Esc` can cancel and the timeout can fire; awaiting the command inline would freeze the REPL. |
| A run only starts from an idle prompt (AS-08) | `Pending` and `AwaitingApproval` already own the bottom of the screen; a third writer there would race the indicator. |
| `[shell]` with four keys, defaults matching `[tools.bash]` | One execution model in the tree, and existing config files keep loading (FR-12). |
